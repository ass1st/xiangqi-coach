# 设计决策与踩坑

> 这份文档回答的是「为什么这么做」，不是「怎么做」。代码在 `index.html`。

---

## 决策一：问「走这里会进入什么样的棋」，不问「这步该走哪」

- **试过**：直接把引擎评分标在棋盘上。
- **问题**：引擎给的是分数，不是计划。+0.5 和 +0.4 的差别对业余棋手没有意义，他不知道这 0.1 差在哪个结构上；也不知道为什么这条线「更好下」。
- **定案**：每条候选必须挂三样东西——属于哪个体系（ECCO 编号）、这个局面是什么性质（对攻 / 阵地 / 简化 / 受压）、这种局面下的三条典型着法思路。
- **代价**：内容要人工建库，不能靠引擎自动生成。引擎分差与局面性质的相关性只有 0.19，一致性低于「全判阵地」的基线，说明性质**必须人工标**。

## 决策二：先答后判，不给提前量

- **试过**：把候选分数直接显示在选项旁边。
- **问题**：一眼看到 +0.5 排第一，就不是在判断，是在照着答案点。练十遍也不会长。
- **定案**：选之前不给任何分数、标签、讲解。四个选项每次随机排序，防止第二遍靠「上次第几个」背答案。
- **代价**：做完之前玩家不知道自己错没错，心理上不如「即时反馈」爽——但即时反馈会污染判断。

## 决策三：套题按主线走，选错不带你出线

- **试过**：选了哪条就走哪条，一路走下去。
- **问题**：错的分支上继续推演，只会越走越偏；走到第 20 手时，残局局面已经完全不是这条体系的样子，讲解也就讲不出这条体系的东西了。
- **定案**：套题里，选错只记在成绩里，棋盘仍按主线推进。错的分支不进棋盘，进轨迹。
- **代价**：玩家看不到「如果我那么走会怎样」——补偿方式是在单题模式里保留「换一条试试」。

## 决策四：结束时先报三件事，再展开

- **试过**：先铺逐步讲解，最后给总分。
- **问题**：玩家已经准备走了，记不住；而且「几分算好」没有参照，分数等于没报。
- **定案**：**收尾三报**——现状 / 预期 / 差距，三句报完才展开整体与逐步说明。分数必须配基线。
- **代价**：要给每套卷定义「至少该拿几分」，这是内容工作量，不是代码工作量。

## 踩坑表

| 现象 | 原因 | 处理 |
|---|---|---|
| 隐藏模式下画布宽为 0，弧半径算出负数 | 布局先隐藏后测量 | 绘制前先判宽高，小于阈值直接返回 |
| 河界文字压住棋子 | 文字画在棋盘上层且未降透明度 | 改成淡色并调整基线 |
| 「兵七进一（吃卒）」名实不符 | 坐标写的是三路兵，红七兵对面才是黑 3 卒 | 换掉整条线，并加落点虚线圈做视觉校验 |
| 结束页棋盘错停在别的节点 | 总评时没有重建最后一手局面 | 单独写一个「重建终局」函数 |
| 妙手显示 undefined | 用名称反查分数，名称对不上 | 改成按 best 标记直接取 |

## 明确没做的事

- **不做眼动追踪**：网页端精度约 4° 视角、帧率 < 30Hz，判不出「跟丢」，测不准就不该拿来评分。
- **不做实时支招**：真人平台封号，这是红线。
- **不做引擎自动生成讲解**：会产出「听着很顺但根本不存在」的计划。
